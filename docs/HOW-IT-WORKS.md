# How the Ledger works

A plain-language guide to the whole project. It is updated at the end of each milestone, so it
always describes what exists today. For the plan and the decision log, see `PLAN.md`; for the
rules Claude Code follows, see `CLAUDE.md`.

**Status:** M0 to M3.5 (core logic), M4a (database, import, quick-add), M4b-1 (HTTP API with
scoped tokens and audit log) and M4b-2a (a runnable server, admin command, production Postgres
driver) are built. Pots, payday, free-to-spend routes, the Angular app, MCP and the Telegram bot are
not built yet (see section 10).

## 1. What it is

A personal finance ledger for one person. It answers one question reliably: **"how much can I
spend until payday?"** To do that it keeps every payment exactly once, separates real spending
from money that only moves (card bills, SIPs, money sent home), and tracks what is already
earmarked (pots) so the headline number is honest.

You log spends in a few seconds ("450 dinner upi"). When the bank statement arrives, the real
rows are matched to what you logged, so nothing is counted twice.

## 2. The five ideas everything rests on

1. **Money is integer paise, never floats.** ₹879.50 is `87950`. Floats cannot represent most
   decimals exactly, and a ledger that is off by a paisa cannot be trusted. Amounts are parsed
   from text digit by digit (`1,23,456.78` never becomes a float). The type `Paise` is "branded",
   so you cannot accidentally pass a plain number where money is expected.
2. **Dates are calendar dates, not moments.** A statement says `05/11/2026`. Stored as UTC
   midnight it would show as 4 Nov in India. So transaction dates are `YYYY-MM-DD` text
   (Postgres `date`), and "within 2 days" means calendar days.
3. **Exactly-once.** Every real-world payment is counted once, whether it came from your quick-add,
   an SMS, or a statement. This is enforced in code, tested with random inputs (property tests),
   and enforced again by the database (a unique key), so a bug cannot silently double-count.
4. **Never guess.** If two things could match, the system does not pick one. It shows both and
   asks you. A wrong silent merge hides a real payment; a question costs five seconds.
5. **The maths is pure and deterministic.** `packages/core` does no I/O (no database, network or
   clock reads) and uses no AI. Same input, same output, always. Anything with side effects lives
   in `packages/api`. An AI assistant (later, over MCP) may *read* and *explain* numbers, but it
   never computes them.

## 4. The life of one payment

You pay ₹450 at a cafe by UPI.

1. **Quick-add.** You type `450 dinner upi`. `parseCapture` (core) turns that into a *pending*
   entry: amount -45000 paise, category `dinner`, method `upi`, today's date, source `manual`.
   `captureEntry` (api) stores it in your bank account. It counts against free-to-spend right
   away, because the money is gone even though the bank has not posted it.
2. **Statement arrives.** You import the bank's CSV. For each row, `planImport` first drops rows
   already stored (re-importing the same file adds nothing).
3. **Matching.** `matchStatement` looks for a pending entry with: same account, a method that can
   appear on this statement (never cash), same sign, same amount, within 2 days. Exactly one
   candidate: **merge in place**. Your entry survives (it keeps your category and memo), takes the
   statement's date, reference and counterparty, and becomes `posted`. No second row is created.
   Several candidates: the row is **held** (not inserted) and you pick which entry it is, or "new".
4. **Reports.** `monthlySummary` splits the month into income, invested, family, and spend by
   category, and reconcile nets out refunds and shared payments so a ₹21,000 ticket purchase that
   mostly came back from friends is not shown as ₹21,000 of spending.

## 5. Core modules (`packages/core/src`)

| Module | What it does | Why it exists |
|---|---|---|
| `money` | parse/format paise | no floats, ever |
| `dates` | date-only type, add/compare days | no timezone drift |
| `domain` | kinds, methods, `isPurchaseFlow` | shared vocabulary |
| `import/csv*`, `demo-mappings` | CSV to rows, per-bank column mappings | banks all differ |
| `import/identity` | row identity = account, date, amount, bank ref or counterparty, plus occurrence number | re-import safe, but two real identical chais stay two |
| `categorise` | ordered user rules: text to category (and optionally kind) | no AI, explainable |
| `transfers` | pairs card-bill payments and own-account moves | transfers are not spend |
| `reconcile` | groups purchase + refund + friends' shares into bundles with a net | real spend, not gross |
| `cycle`, `payday`, `pots` | statement/due dates, salary waterfall, derived pot balances | plan money before spending it |
| `free-to-spend` | the headline number, as lines that sum to it | explainable |
| `forecast` | daily burn and runway to payday | rounds the safe way |
| `simulate` | "can I afford X" by UPI, card, or Slice in 3 | decide before paying |
| `summary` | monthly split by kind and category | "where did my salary go" |
| `capture` | the quick-add grammar | fast, deterministic logging |
| `matching` | manual/SMS entry vs statement row; SMS vs manual duplicates | exactly-once |

### Transaction kinds

`spend` (purchases and their refunds), `income`, `transfer` (own-account moves, card-bill payments),
`investment` (SIP: saved, not spent), `family` (money sent home). Only `spend` and `income` are
"purchase flow": transfers, investments and family money are planned in pots / the payday
waterfall and kept out of reconcile, burn and free-to-spend.

### Payment methods and statuses

Method is how you paid: `upi`, `card`, `cash`, `netbanking` (UPI is a method drawn from a bank
account, not an account). Status is `pending` (you logged it, the bank has not posted it) or
`posted` (it appeared on a statement). Cash is always pending: it never appears on a statement,
so it never matches one.

### The quick-add grammar

`[spent|paid|got|received] <amount> [on|for|at] <category> [memo words]`, plus a method
(`upi card cc cash netbanking nb`) and a date (`today yesterday YYYY-MM-DD`) anywhere.
`+500` or `got` means income. The default method is UPI. The text is untrusted, so it is
length-capped, control characters are stripped from the memo, and the parser never throws.

## 6. The database (`packages/api/src/db`)

Twelve tables, defined in `migrations.ts` and typed in `schema.ts`. The ledger itself is three of them (the API-token and audit-log tables are described under the security model):

- `accounts`: bank, card, savings or cash; cards carry statement day and due day.
- `import_batches`: one row per import that changed something (source, row count, file hash).
- `transactions`: everything else. Signed `amount` in paise (`bigint`), `date` (`date`), `kind`,
  `method`, `status`, `source`, `identity` (the statement row's identity, set exactly when
  `posted`), plus category, memo, counterparty, ref.

The database enforces the rules too, so a bug in code cannot corrupt the ledger:

- amount is never zero; kind, method, status, source are from fixed lists;
- `posted` if and only if `identity` is set;
- imported rows are always posted; cash is always pending;
- `unique (account_id, identity)`: the same statement row cannot exist twice.

Then the planning tables (migration `003_planning`), which feed the free-to-spend number:

- `settings`: exactly one row: payday day (default 7, a placeholder until you confirm), what to
  do when payday falls on a weekend (default: the previous weekday), and how card bills count
  (`all_outstanding` or `due_before_payday`).
- `pots`: named reserves. Kinds: `buffer` (safety money), `bill` (set aside for a bill; may have a
  due date or cover a card) and `spend`. A pot never stores its balance.
- `pot_movements`: the pot journal. Every deposit or withdrawal is one row; a pot's balance is the
  sum of its rows. The journal is append-only (the database refuses UPDATE, DELETE and TRUNCATE),
  so history cannot be rewritten; a mistake is fixed by adding a correcting row.
- `payday_runs` and `payday_rules`: the ordered list of "fixed / percent / remainder" splits and
  the record of each time one was applied. The run id is the idempotency key.
- `scheduled_items`: money that will leave on a known date, once or monthly (rent, recharge).
- `balance_checkpoints`: "this account held this much on this date", stated by you (cards:
  negative when money is owed). Today's balance is the latest checkpoint plus the transactions
  dated after it. This avoids pretending we can know balances from partial statements.

**Drivers.** `bigint` comes back as a safe JS number (an error if it ever would not fit) and
`date` as plain `YYYY-MM-DD` text. **Tests** run on PGlite, which is real Postgres compiled to
WASM running in-process: the same SQL, constraints and transactions as production, no Docker.
The small dialect connecting Kysely to PGlite is in `pglite-dialect.ts`, written in-repo instead of
adding a third-party package.

## 7. Services (`packages/api/src`)

- `captureEntry(db, text, context, newId, accountId?)`: parse, pick the account that owns the
  method (one bank account for UPI, one card for card, one cash account), insert a pending row.
  Zero or several candidate accounts is an error asking you to say which.
- `previewImport(db, request)`: runs the whole plan, writes nothing, and returns what would
  happen: duplicates to skip, rows to insert, entries to merge, rows held as ambiguous.
- `confirmImport(db, request, newId)`: the same plan inside one database transaction. A batch is
  written only if something changed; any failure rolls back everything, including merges.
  Held rows stay unwritten, so importing the same file again after you decide re-presents them.
  `choices` maps a held row to a pending entry id, or `"new"`.
- `planning-service.ts`: everything behind pots, payday, scheduled items and balances.
  `computeFree(db, today)` is the headline number. It gathers the pieces below, hands them to the
  pure `freeToSpend` in core, and returns the number with every line that went into it:
  1. balances now (checkpoint plus later transactions; cash entries count even while pending);
  2. minus what you owe on cards (either everything, or only what falls due before payday);
  3. minus buffer and bill-pot reserves;
  4. minus pending bank entries not yet on a statement (and dated after your last checkpoint,
     so nothing is counted twice);
  5. minus scheduled outflows between today and the next payday.
  If any account has no checkpoint it refuses with the list of missing ones instead of guessing,
  and it warns when a checkpoint is more than 7 days old.
  Applying a payday is idempotent: the same run id with the same values is a no-op that returns
  the original result, the same id with different values is refused.
- `analysis-service.ts`: the read side built on top of that.
  - `forecastFor` reconciles the trailing window (default 14 days), turns the bundles into spend
    events (a refunded purchase counts at its net; transfers, investments and family transfers
    never count), takes the daily burn (rounded up) and projects free money to payday. Rows dated
    in the future are ignored so they cannot hide a purchase that already happened.
  - `runSimulation` answers "can I afford this?" for UPI, card or Slice in 3 using the same
    free-to-spend number. Slice in 3 assumes no minimum and no fee until those terms are
    verified in the app, and the response says so under `assumptions`.
  - `reconcileRange` runs the reconcile pass over a date range (with a margin so a pair that
    straddles the edge is seen whole) and returns bundles, the review queue and the transactions
    they refer to.
  - `updateTransaction` changes only `category` or `kind`: amounts, dates and statement identity
    can never be edited through the API.

## 8. The HTTP API (`packages/api/src/app.ts`)

Express 5 with zod validation. `createApp({ db, newId, ... })` returns the app; tests start it on a
random port and call it with `fetch`. Planning routes live in `planning-routes.ts`, shared request
helpers in `http-support.ts`.

| Route | Scope | What it does |
|---|---|---|
| `GET /health` | none | liveness |
| `POST /capture` | capture | `{ text }` becomes a pending manual entry |
| `POST /imports` | full | preview: send `{ accountId, mappingId, csv }`, get what would happen (no writes) |
| `POST /imports/confirm` | full | same body plus optional `choices`; commits in one transaction |
| `GET /transactions` | read | filters: `from to category q status limit` |
| `GET /summary?month=YYYY-MM` | read | `monthlySummary` over that month, with reconcile bundles |
| `GET/POST /tokens`, `DELETE /tokens/:id` | full | list, create (secret shown once), revoke |
| `GET /settings` (read), `PATCH /settings` (full) | | payday day, weekend rule, card exposure mode |
| `GET /pots` (read), `POST /pots`, `PATCH /pots/:id` (full) | | pots with derived balances |
| `GET /pots/:id/movements` (read), `POST /pots/:id/movements` (full) | | the pot journal; manual, spend and true-up entries |
| `GET /payday/rules` (read), `PUT /payday/rules` (full) | | the ordered payday split, replaced as a whole |
| `POST /payday/preview` | read | what a given amount would split into; writes nothing |
| `POST /payday/apply` | full | `{ runId, amountPaise, date? }`: journals the split; repeating the same run is safe |
| `GET /scheduled` (read), `POST /scheduled`, `DELETE /scheduled/:id` (full) | | one-off or monthly outflows |
| `GET /balances` (read), `POST /balances` (full) | | record "this account holds X today" (never a future date) |
| `GET /free` | read | the free-to-spend number with its lines, balances and warnings; 409 listing missing balances |
| `GET /forecast?windowDays&estimator` | read | daily burn, projected free money on payday, runway in days |
| `POST /simulate` | read | `{ amountPaise, method: upi\|card\|slice_in_3, cardAccountId? }`: what a purchase would do to free-to-spend. A calculation, never a write |
| `GET /reconcile?from&to` | read | refund/split bundles for a date range (default last 30 days) plus the review queue |
| `PATCH /transactions/:id` | full | fix a transaction's `category` (or clear it with null) or `kind` |

**Import is stateless.** The client sends the same CSV to preview and to confirm (confirm also
carries your `choices` for ambiguous rows). The server recomputes the plan inside the commit
transaction, so there is no preview token to expire or forge, and the result always reflects the
database at the moment of commit.

### Security model

- **Scoped tokens.** `capture` can only add pending entries (safe to keep on a phone or in a bot),
  `read` can only read (for MCP and the bot), `full` can do everything including managing tokens.
  Every route declares the scope it needs; the check is in one place (`guard`).
- **Token storage.** A token is `led_` plus 256 random bits. Only its sha256 is stored (a
  database leak does not reveal usable tokens); the secret is shown once at creation. Revoking
  takes effect on the very next request.
- **Audit log.** Every mutation writes a row (who, what, when) with counts and ids only, never
  memos or counterparties. The table refuses UPDATE, DELETE and TRUNCATE (database triggers).
- **Rate limits.** Per token, in memory: 60 captures and 300 other requests per minute (config).
- **Validation.** Strict zod schemas reject unknown fields; errors list the field path and rule but
  never echo what you sent. Bodies are size-limited (10 KB, or 2.5 MB for imports).
- **Errors** are always `{ code, message, details? }`; unexpected failures return a generic 500 and
  log only the error class name.
- **Headers.** `no-store`, `nosniff`, and a locked-down CSP are set by hand. `helmet`, CORS and
  cookie sessions arrive with the web app.

## 9. Running the server

Needs a Postgres 16 database and its URL.

```
export DATABASE_URL=postgres://user:password@localhost:5432/ledger
pnpm --filter @ledger/api admin add-account --id bank --name "Main bank" --kind bank
pnpm --filter @ledger/api admin add-account --id cc --name "Card" --kind card --statement-day 5 --due-day 25
pnpm --filter @ledger/api admin create-token --name laptop --scope full   # prints the secret ONCE
pnpm --filter @ledger/api start                                           # 127.0.0.1:3000
```

- `HOST` (default `127.0.0.1`) and `PORT` (default `3000`) are optional. Loopback is the default
  on purpose: put a reverse proxy or a private network in front before exposing it.
- Migrations run automatically when the server (or the admin command) starts.
- The admin command works on the server host only; there is no HTTP route that can create the
  first token, so a stranger who finds the port cannot bootstrap access.
- `SIGTERM`/`SIGINT` stop accepting connections, finish in-flight requests, then close the pool.
- Configuration errors name the problem but never print the database URL (it contains a password).
- `bigint` and `date` are parsed by the `pg` pool exactly as in the test client, and the driver is
  tested against a real Postgres in CI (a service container) and locally when `TEST_DATABASE_URL`
  points at a database whose name ends in `_test` (the suite recreates its schema).

## 10b. The web app (`packages/web`)

So far: the look and the parts every screen is built from, plus six real screens: **Connect**,
the **Dashboard**, **Transactions**, **Import**, **Reconcile** and **Pots**.

- **Design tokens** (`src/styles/tokens.css`): every colour, size, radius and duration lives in
  one file as CSS variables. Dark is the default; light follows your phone's setting or your
  choice. A test checks that every text colour is readable on every surface it is used on (the
  WCAG AA contrast standard), in both themes, so the palette cannot quietly become hard to read.
- **Components** (`src/app/ui`): money, button, chip, badge, card, and the empty / loading / error
  message. Screens will be assembled from these rather than styled one by one.
- **Money** is always drawn by `ui-money`, which formats integer paise with the same function the
  API uses (`formatINR` from core), so a number can never read differently on screen than in the
  API. Digits are fixed-width so columns of amounts line up.
- **Gallery** (`/gallery`): one page showing every component in both themes with made-up data. It
  is how a design change gets reviewed without needing real numbers on screen.
- Accessibility basics are built in: a skip link, keyboard focus ring, state never carried by
  colour alone (the text says "posted", the sign is in the number), and reduced-motion support.

**Connecting.** Until the proper login exists (see section 11), you paste an API token on the
Connect screen. The token is kept in this browser tab's memory only: never in the address bar, never
in browser storage, never printed. Reloading the page asks for it again. The page checks it by
asking the API for your settings; a wrong token is refused with a plain message. If the API ever
answers "not authorised" later (for example you revoked the token), the tab forgets the token and
sends you back to Connect. The token is attached only to calls to the API, never to anything else.

**Talking to the API.** Every answer is checked before it is used: money must be a whole number of
paise and dates must be real calendar dates, otherwise the screen shows an error naming the field
instead of a wrong number. During development the web server forwards `/api/...` to the API on
port 3000 (the API deliberately allows no cross-site calls), so run both side by side.

**The Dashboard** (`/dashboard`) answers "what can I spend until payday?":
- The headline number is free-to-spend, with days left and the payday date. Warnings from the API
  (for example "this balance is 9 days old") appear under it.
- **How this is worked out** lists every line behind the number: your balances, the money set
  aside for cards, pots and bills. The lines add up to the headline, so nothing is hidden.
- **Forecast**: your average daily spending over the last 14 days, what you would have left on
  payday, and whether the money lasts. This is said in words, not just colour. If the reserves
  already use up everything, it says "Nothing free" instead of a runway.
- **Pots**, with a progress bar toward each target, **Card dues** (what you owe and the next due
  date) and **Due before payday** (the scheduled bills that were taken off the headline).
- **First run**: if an account has no balance yet the API cannot work the number out. The page then
  asks for your starting balances ("what does your bank app say today?"). For a card you type what
  you owe as a positive number. Amounts are read as exact rupees and paise, never as decimals.
  Saving needs a full-access token; a read-only token gets a clear message saying so.

**Transactions** (`/transactions`) shows one month at a time:
- **Month bar**: step back and forward; you cannot go past the current month (India time).
- **At a glance**: income, spent, invested, family and left over, from the same monthly summary the
  API computes (every payment counted exactly once). Transfers between your own accounts are
  mentioned but never counted as spending. Below it, the biggest spending categories.
- **Search and filters**: search by name or note, filter by Pending / Posted, and by kind. Status
  and search are answered by the API; kind is applied on the page. The list shows the latest 200
  rows of the month and says so if there may be more.
- **Each row** shows the name (counterparty, else your note), date, account, payment method, a
  Pending/Posted label, the kind, the category and the amount with its sign in the text.
  Anything from a bank statement is shown as plain text, never as markup.
- **Edit** changes only the category and the kind, the two things you can legitimately fix after the
  fact. Amount, date and name come from the bank and are never editable. Only what changed is sent;
  an emptied category clears it. Category names already in use are offered as suggestions so the
  spelling stays the same. After a save the month's totals refresh without the list flashing.
  Saving needs a full-access token; a read-only token gets a clear message.

**Import** (`/import`) brings in a bank or card statement (a CSV file) in three steps. Nothing is
saved until the last one.
1. **Choose.** Pick the account, the statement layout (the demo layouts for now: FakeBank savings
   and DemoCard credit card) and the file. The file is read in your browser and sent only to your
   own API; the page keeps it in memory just long enough to import it, and forgets it afterwards.
   Cash accounts are not offered, because cash never appears on a statement. An empty file, or
   one over about 2 MB, is refused with a plain message.
2. **Review.** The API works out what *would* happen and the page shows it as four counts: new
   transactions, entries you added by hand that the statement would complete, rows already
   imported earlier (skipped, so nothing counts twice), and rows that need your decision. Lists
   below show the new rows and the entries that would be completed. If a row cannot be read
   exactly (a bad date or amount), the page lists the first few problems and blocks the import:
   a statement is never half-read.
3. **Decide the ambiguous ones.** Sometimes one bank row could be one of several entries you added
   by hand (for example two ₹175.39 bakery payments a day apart), or two identical bank rows
   compete for the same entry. The page asks, one question per row: pick the right entry, or say
   "None of these: it is a separate payment". Each choice re-asks the API for the plan, so the
   counts always reflect your choices; the picker stays open so you can change your mind. If you
   pick the same entry for two rows, the page tells you. Rows you leave undecided are left out of
   this import and come back the next time you import the same file.
4. **Import.** One button, with the number it will import. The API repeats the whole calculation
   from the same file and choices inside one database transaction, so a stale review can never
   count anything twice. The result says how many were added, completed, skipped and left out, and
   links to Transactions.

Importing needs a full-access token; with a read-only token you can open the page but the preview
explains that it needs a full-access one. Names and notes from the file are shown as plain text,
never as markup.

**Pots** (`/pots`) is where money is set aside, and where every change to a pot is made:
- **The list.** Each pot shows its kind (Safety buffer, Bill or Spending), what is in it, a progress
  bar toward its target, its due date, and, for a bill pot that pays a card, which card. The
  balance is never stored: it is the sum of the pot's history, added up by the API.
- **New pot.** Name, what it is for, an optional target, and (for a bill) an optional due date and
  an optional card it pays. Amounts are read as exact rupees and paise. Only bills can have a due
  date or a card, the same rule the API enforces.
- **Edit.** Name, target and due date can change; the kind and the card cannot. Only what changed is
  sent, and emptying the target or the due date clears it.
- **Move money.** Pick "Put money in" or "Take money out", type a plain amount (the sign is added
  for you), and say why (moved by hand, spent from the pot, or a correction). If you take out more
  than the pot holds, a note says its balance will go below zero; it is allowed, because a
  correction can legitimately need it. The date is left to the server, which uses today in India.
- **History.** The pot's journal, newest first, with a plain-words reason for each line. The
  journal only grows: nothing can be edited or deleted, so a mistake is fixed by moving money the
  other way and choosing "Correction".
- **How pots affect the Dashboard.** Safety buffers and bills are kept out of free-to-spend; a
  Spending pot is not. A bill pot that pays a card is compared with what the card owes, and the
  larger of the two is kept out. The page says this in one sentence at the top.

Changing a pot needs a full-access token; with a read-only token you can look, and a change shows a
clear message instead.

**Reconcile** (`/reconcile`) shows how payments that cancel each other out were matched. A refund
undoes a purchase; a friend's share pays back part of a bill. If both were counted as they are, you
would look like you spent twice. The API pairs them up and counts the pair at its net. This page only
shows the result and changes nothing, so it works with a read-only token.
- **Month bar.** One month at a time, today's month first; you can go back but not past this month.
  Four numbers sit under it: matched pairs, groups to check, payments needing review, and ordinary
  payments (everything with nothing to match, counted on its own).
- **Please check.** The two sides have different names (a friend's name against a restaurant), so the
  match is a suggestion. The group is already counted at its net, so confirm it really belongs
  together. A group of four or more payments (two paid out, two paid back, the same amounts) says
  "payments that match in any order": every way of pairing them gives the same total, so nothing is
  guessed.
- **Matched.** The same name is on both sides (an airline and its refund). These are safe to net.
- **Need review.** Payments that could be paired in more than one way, or too many to pair safely.
  Nothing in them is netted: each counts on its own until someone decides.
- **Not possible yet.** The page cannot confirm or reject a match, because the API has no way to
  record that decision. Adding one is a new write endpoint, which needs your explicit go-ahead
  (see PLAN.md section 15).
- Names from the bank are shown as plain text, never as markup. A payment the API did not describe
  is left out of its card instead of being shown wrong.

## 12. Decisions worth remembering

- Postgres over MongoDB: relational integrity and real constraints suit money.
- `pg` over postgres.js: it has the stock Kysely dialect and the widest tooling; no extra adapter code on the money path.
- Kysely over an ORM: typed SQL you can read; no hidden queries.
- PGlite for tests: real Postgres semantics without Docker, so tests run anywhere.
- Strict matching by default (exact amount): a wrong merge hides a payment. Allow a small fee
  tolerance per account later if a bank really adds fees.
- Balances come from checkpoints you state, not from guessing: a bank statement shows a running
  balance only for the rows it contains, so the app asks for "what does your bank app say today?"
  and counts forward from there.
- Pot balances are derived from an append-only journal, never stored, for the same reason the
  ledger is append-friendly: there is no number to drift out of sync with its history.
- Plain CSS with variables for the web app instead of SCSS: the design system is just variables,
  so no preprocessor (and no extra dependency) is needed.
- Tokens over a shared secret header: each client gets its own scope, can be revoked alone, and leaves an audit trail.
- No hosted AI in v1: Claude reads through MCP on your machine; the numbers come from core.
